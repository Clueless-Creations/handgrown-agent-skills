Your runtime may show Handgrown's tools with a prefix (for example `Handgrown:` or `mcp_handgrown_`). The names below are the base names. Handgrown's server instructions, tool descriptions and the guides its tools return are newer than this skill; where they differ, follow them.

## What a connection can do

Discovery (`handgrown_capabilities`) lists the exact tools; the list is the level.

- **Read**: only `query` tools. You read and report.
- **Read and draft**: also direct commands that apply at once (such as `handgrown_task_create` and `handgrown_task_note_add`), proposals a person approves in Handgrown (`handgrown_propose_*`, `handgrown_offer_draft`), requests queued under a mandate the brand set, when listed (`handgrown_action_request` and the correspondence, call and retailer-form request tools) and `handgrown_application_decision`, which applies, proposes or holds under the brand's own level.
- **Act for me**: everything above, and Handgrown applies each proposal for the signed-in person in the same call, application decisions included. Handgrown keeps some kinds for a person even then, caps how many it applies a day, and offers this level only where the brand allows it.

## The loop

1. **Discover.** Call `handgrown_capabilities` on the connector your Handgrown workspace memory names, or the one handgrown-getting-started adds, at the start of each session, and again after Handgrown says something changed. Use only that connector's tools. It lists the tools you may call now, which workflows are available and why the others are not, and the console pages for anything only a person can do.
2. **Read.** Read the live record before you change it. Take every id, version and link from results. Lists are paged: pass `next_cursor` as `after` until it is null. In writing, say how many pages you read before you call a list complete; on a call, say only whether you read all of it.
3. **Act with the strongest tool you have.**
   - **A direct command.** Run it. A typed `ok` or `applied` result is the proof: report it as applied by you for your person, without reading it again. Never say they approved it.
   - **A proposal.** It belongs to an open task (recruiting and event proposals need a general one). Use a task you created for this goal, found with `handgrown_task_list`, or create one with `handgrown_task_create` and a title that names the goal. Do not reuse a task you did not create for this goal. Then:
     - **At Act for me, Handgrown applies it in the same call.** Send it with a request_id; its result's `act_for_me` says how it went, as the tool's description explains. Do not call `handgrown_approval_apply` for it, except for `earlier_approval` below. Report `applied` as done by you for your person, never as approved by them, share no approval link, and if `record.items_failed` is above 0, say which parts did not apply. For `nothing_applied`, the approval was used but no part took effect, so nothing changed: say so, give `reason_text` in plain words, never report it as done, and read the record before sending a new proposal with a new request_id. For `not_applied`, nothing changed: post the `continue_url` as a named link, such as [Approve the Orlando plan](<continue_url>), give `reason_text` in plain words, stop a batch there, and carry on with unrelated work. For `not_pending`, `expired` or `invalidated`, read `handgrown_approval_get` and report its status.
       - `unconfirmed`: Handgrown could not confirm the apply. Send the same proposal once more with the same request_id. If it is still `unconfirmed`, post the `continue_url` as a named link, say the person decides it there, and stop: never send it a third time or apply it yourself.
       - `earlier_approval`: the same change was already waiting in an approval made earlier; nothing was applied in this call. Read it with `handgrown_approval_get`. If it is what the person asked for, ask in this chat, then apply it with `handgrown_approval_apply` as the bullet on that tool below says, and if that comes back `not_applied`, post its link as above. Say it is done only once a fresh `handgrown_approval_get` shows it approved.
       - At Act for me, make an application decision with `handgrown_propose_application_review`: it is applied in the call like any other proposal. `handgrown_application_decision` and `handgrown_propose_prepared_application_review` are not listed at this level.
     - **A proposal that waits at Act for me** counts as a refusal toward a hold on this connection: never send it again or try to apply it, except as the next bullet says. Pass on its `reason_text`, and for the daily limit the time it resets (`act_for_me.usage.resets_at`). Suggest connecting you again only after the person or the operator says Handgrown widened the Act for me settings since you connected (a widening reaches only an assistant connected after it), never otherwise. For `not_in_scope` with no class, a limit no setting lifts, never ask them to connect you again for it.
     - **`handgrown_approval_apply` is for an approval made earlier:** to reject one of your own that a newer proposal replaces, to apply one of your own again after the daily limit resets, or to apply an `earlier_approval`. Ask in this chat first; do not send them to the browser unless apply is missing or returns `not_applied`. Never use it on a `handgrown_propose_prepared_application_review` approval: it waits for a person, and each try is a refusal. Read `handgrown_approval_get` first and pass what the tool's description lists, with a new request_id.
     - **Without the apply tool,** post the `continue_url` as a named link and say the proposal waits for their approval. They open it in the browser where they use Handgrown and sign in once if asked. When they say it is approved, read it yourself. Discovery marks approvals `available` only when the apply tool is listed; otherwise they stay console-only.
   - **A queued request (when listed).** Send it, then read its status tool (`handgrown_action_status` or the matching status read). Report it as queued, not sent, until the status shows otherwise. If no mandate covers it, say a brand admin sets mandates in Handgrown.
   - **No tool does it.** Name the console page discovery gives; if it gives none, say Handgrown doesn't do that from here yet. Never say Handgrown has or lacks a feature you have not read from its tools. Carry on with the rest.
4. **Follow through.** Read `handgrown_approval_get` yourself rather than asking the person whether they approved. Report the status it returns: pending, approved, rejected, expired, invalidated or canceled. Approval is not delivery and it is not payment. When one approval covers several items, report each as completed, failed or open.
5. **Confirm only what a receipt does not prove.** Read again for a proposal's status, a queued request, an uncertain or `error` outcome, a send through another system, and before you say anything is live to the public. When the person relies on a fact, give its source and the time you read it, in writing.

## Refusals

Handgrown's MCP layer decides what you may do. A refusal says where the line is now and what to do next:

- `invalid`: nothing was written. Correct the arguments as the message and the tool's own input schema say, every field it names at once. The corrected call is a changed write, so it gets a new request_id. If the message names no field, read the current record again and make one corrected attempt. If that is refused too, stop and give the person the message word for word, with the task and any approval it touches.
- `denied`: the signed-in person lacks that access in this brand. Say so, say that a brand admin can grant it in Handgrown, and carry on with what you can do.
- `unavailable`: the message names the reason and a console page that does the job. Pass both on plainly.
- `conflict`: the record already exists, the target changed, or this request_id was used with other content. Read `handgrown_operation_log` and the record, then continue from the current state. Your earlier call has often already worked.
- `error`: the outcome is unknown, not failed. Follow the retry steps below.

Pass on who can lift a limit only as the reason says. The person can connect again and pick a higher level if Handgrown's page offers one. Never resend a refused call with a new request_id.

## Retries and request_id

- Before each write, generate a UUID request_id and keep it with the exact arguments. Reuse it on every retry of that write, from this assistant or any other the same person uses with this workspace: Handgrown returns the original record or a conflict, never a second one. A new request_id is a new write; use one only for a deliberately changed command, once you know the first outcome.
- After a timeout, a lost reply or an `error`: read `handgrown_operation_log`, then look for the record with its own read (`handgrown_task_get`, `handgrown_task_context`, `handgrown_approval_get` or its status tool). If it is there, the write happened: report it. If not, resend the identical command once with the same request_id and say so. If that also fails, or you lost the request_id, stop and report the write as unconfirmed.
- Before you resend a proposal, read `handgrown_approval_get` so the person is not asked twice. For queued requests, read their status tool instead of resending.

## Pending approvals

A new proposal does not replace a pending one. Proposals for different targets, such as two cities and a form, can wait together, and the person approves them in one visit. When the person asks for several changes, or changes something you have just proposed, put everything they asked for in one proposal where the tool takes one (the recruiting plan does), rather than one proposal per edit. If a result lists other pending approvals for the same target (`other_pending`), post the one link to use as a named link, say it is the right one, and ask them to reject the others (null means Handgrown could not tell). At Act for me, reject the ones this connection proposed yourself, with `handgrown_approval_apply` and `decision: reject`; and after an `applied` result, post no approval link at all: say it is done, and in plain words which others still wait. Do not ask anyone to reject an approval you did not make for this goal. Approvals expire after 24 hours.

## Applications

- Read `handgrown_recruiting_policy` first. `available: false` means only Handgrown can switch automatic levels on for this workspace; a brand admin cannot. Otherwise `you_may_now` says what you may do on your own right now, and why not.
- At Act for me, decide with `handgrown_propose_application_review`, and stop a batch at the first `not_applied`. Otherwise decide with `handgrown_application_decision`, using the generation, candidate_binding and workflow version you inspected, a one-line reason, a request_id, and a task_id so that a decision you may not apply becomes a proposal.
  - `applied` means it is done. Say it can be undone with `handgrown_application_return_to_review`.
  - `proposed` means it waits at `continue_url` while the approval is pending.
  - `held` means nothing was done. Send the same request_id once more with a task_id, or prepare a proposal with `handgrown_propose_prepared_application_review`. Either proposal waits for the person at its link.
  - After an error or no answer, retry once with the same request_id. If it still fails, read the operation log before you propose.
- Explain a reason in plain words, and never argue with it or retry it with a new request_id:
  - `gate`: only Handgrown can switch automatic levels on for this workspace.
  - `no_policy` or `level`: the brand's level does not cover this. A brand admin can choose one in Handgrown under Assistants > Assistant levels, while `available` is true.
  - `paused` or `expired`: a brand admin resumes or renews the level in Handgrown, under Assistant levels.
  - `authorizer`: the admin who turned the level on lost the access it needs; another admin renews it.
  - `people`: the signed-in person is not on the level's list. A brand admin can add them.
  - `not_permitted`: this always needs a person's approval today (accept and deny). Give the link.
  - `person_handled`: a person already decided or returned this application, so it stays with people.
  - `criteria`: this application does not meet the rules for an automatic decision, for example because it is a test record. A person decides it.
  - `cap`: the brand's daily limit is used up. Say when it resets (`usage.resets_at`) and propose meanwhile.
  - `grant`: the signed-in person lacks edit access in this brand.
- Judge only against criteria the brand stated, and ask if it stated none. Quote answers exactly and briefly. A missing answer is unknown, not a no. Never read anything into a name, photo, accent, voice or writing style.
- Put applicant answers outside Handgrown only when your person asks, to a named place whose readers may see them. Never put them in memory or in a shared channel by default.

## Notes and brand knowledge

- **When a task's goal is done,** close the task if discovery lists a tool that does. Otherwise add one closing note saying what is done and where it lives, and do not ask the person to close it; today only a person closes a task, in Handgrown.
- `handgrown_task_note_add` saves context the person chose to share with everyone in the workspace. It needs an open task and that task's current version: read `task_version` from `handgrown_task_get` or `handgrown_task_context` first. If no open task fits, create a general one for the goal, then add the note. A note is one line of up to 4,000 characters with no web or email addresses, and it carries a source label. Its `ok` result is the proof.
- Notes, and an earlier assistant's "done", are context, not proof. The record itself is the proof.
- `handgrown_workspace_context` holds the brand's attributed knowledge. Where it differs from a profile memory that is not an identity field, it wins.

## Drafts and copy

Decide copy defaults yourself: the wording, the tone, the length and which details from the brand's site and Handgrown to use. Write the draft, show it, then offer one change in a line, such as "Want it shorter?" Ask the person only for a fact you lack, never for permission on a content choice. Public copy uses Handgrown's words from your instructions; for recruiting posts, follow handgrown-recruiting-posts.

## Reporting

Lead with the answer. Follow it with the few facts that change the decision, giving each number with its period and what it is out of. Say what is missing and what you could not read. Describe states in plain words: write "the store hasn't been asked", not `not_requested`. Say spots or goal, not rep target. End with one next step. Never volunteer ids, versions, digests, tool counts or internal system names (a capability check, that Foldie is off) unless the person asks: say what it means for them in plain words, such as "I can set up recruiting and apply it for you" or "Handgrown keeps this one for you to approve".

Give every link as a named link in writing, such as [Approve the Orlando plan](<continue_url>) or [<Brand> ambassador application](<public_url>), never the bare address.

**On a voice call**, follow the call line in your instructions: sum up, never read back a page, plan, list, message or tool result, say the link is in our chat, and keep counts of pages read, sources and read times for writing.

## Connection

If a call says the connection is missing or ended, run handgrown-getting-started. The person can see and end connections in Handgrown under Settings > Assistants. Ending a connection there stops your next call. It does not delete what you keep in your own memory.
